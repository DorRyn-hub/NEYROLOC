# Сохранение и восстановление NEYROLOC

Репозиторий: https://github.com/DorRyn-hub/NEYROLOC (приватный).
Исходники и текущая версия приложения находятся в ветке **main**.
Постоянная ветка **version-control** является default branch: она содержит инструменты
восстановления, которые не исчезают при возврате main к старому снимку.
Для просмотра и скачивания приложения выбирайте **main** в переключателе веток.

## Обычная работа

Перед новой работой:

```sh
git fetch origin --tags
git status
git rev-list --left-right --count HEAD...origin/main
```

Первое число — только локальные коммиты, второе — только удалённые. Если второе
ненулевое, сначала синхронизируйте историю. Для чистой папки достаточно
`git pull --ff-only origin main`. Если есть собственные изменения, сохраните их
в отдельной ветке или stash и объедините без force push.

После законченного изменения:

```sh
QT_QPA_PLATFORM=offscreen python3 -m unittest discover -s tests -v
git add <конкретные-файлы>
python3 scripts/check_repository.py --index
git commit -m "Краткое описание изменения"
git push origin main
```

Используйте Python с установленными зависимостями проекта. Дополнительные проверки
выбирайте по изменению; сборки мобильных приложений требуют соответствующих SDK.
Если push завершился ошибкой, новая версия остаётся только локально.

## История и скачивание старой версии

На GitHub: переключитесь на **main** → **Commits**. Выберите коммит и **Browse files**;
для скачивания снимка используйте **Code → Download ZIP**. Теги находятся в разделе
**Tags**; исходный безопасный снимок отмечен **v1.0.0**.

Локально:

```sh
git log origin/main --oneline --decorate
git show <SHA>
git archive --format=zip --output=../neyroloc-old.zip <SHA-или-тег>
```

Для новой копии текущих исходников явно укажите main:

```sh
git clone --branch main https://github.com/DorRyn-hub/NEYROLOC.git
cd NEYROLOC
brew install gitleaks
python3 scripts/install_hooks.py
```

Окружения, модели и личные настройки нужно восстановить отдельно.

## Восстановление через GitHub Actions

1. Откройте **Actions → Восстановить версию → Run workflow**.
2. В поле ветки выберите **version-control**.
3. В поле версии вставьте **полный SHA из 40 символов** или точное имя тега,
   например `v1.0.0`. Нажмите **Run workflow**.
4. Дождитесь зелёного результата. В отчёте появятся выбранный SHA, новый SHA,
   хеш дерева и резервный тег `before-restore/...`.

Восстановление создаёт **новый коммит** в main. Его дерево файлов точно совпадает
с выбранным снимком, а родителем остаётся предыдущая вершина main: все более новые
коммиты сохраняются в истории. Перед обновлением создаётся уникальный тег предыдущего
состояния. Тег и обновление main отправляются атомарно. При конкурирующем изменении
операция отклоняется целиком; повторите её после проверки истории.

Можно выбирать только коммиты/теги из истории main. Снимки с секретами, приватными
данными, сборками или запрещённой служебной атрибуцией отклоняются. Старые локальные
ветки с окружениями и архивами не являются безопасными версиями для восстановления.
Чтобы отменить восстановление, запустите тот же workflow с тегом `before-restore/...`
из предыдущего успешного запуска.

## Синхронизация папки после удалённого восстановления

Сначала остановите редактирование и проверьте `git status`. Для чистой папки:

```sh
git fetch origin --tags
git pull --ff-only origin main
git rev-parse HEAD
git rev-parse origin/main
```

Два последних SHA должны совпасть. Если есть свои изменения, сначала сохраните их:

```sh
git stash push -u -m "Перед синхронизацией восстановления"
git pull --ff-only origin main
git stash pop
```

При конфликтах не применяйте reset/force: сохраните stash и объедините изменения.
Игнорируемые конфиги, базы, окружения, модели и резервные копии не входят в снимок
и не откатываются. Вложенный iOS Git может показать изменения после синхронизации
umbrella-исходников — его отдельная история не переписывается.

## Что исключено из GitHub

- Реальные `.env`, конфиги с ключами, токены, credentials, cookies, приватные ключи,
  signing/provisioning-файлы. Безопасные `.template`/`.example` сохраняются.
- Чаты, sessions, пользовательские данные, рабочие базы и registry, логи, сетевые дампы.
- `.venv`/venv, IDE-состояние, caches, bytecode, runtime-зависимости.
- Сборки `.app`/APK/IPA/DMG, dist/deployment/build/output, бинарные модели и архивы.
- Приватные backup-файлы, локальные отчёты и инструкции с личным контекстом.

Исходники активного приложения, архивного CLI, iOS/Android, тесты, зависимости,
лицензии, ресурсы и безопасная документация сохраняются. Ничего из исключённого
локально не удаляется. Старые локальные ветки сохранены; их нельзя отправлять целиком.

## Проверки и защита истории

`scripts/install_hooks.py` устанавливает pre-commit, commit-msg и pre-push guards
через `.githooks`, проверяет наличие **gitleaks** и настраивает `pull.ff=only`.
Проверяется весь staged snapshot, а перед push — вершина и все новые коммиты,
метаданные и ссылки. Запрещены удаление remote refs, замена тегов и non-fast-forward.
Сканер не выводит значения найденных секретов. Любой отказ проверки блокирует отправку.
Hooks нужно устанавливать в каждой новой копии; GitHub не устанавливает их автоматически.

GitHub API 11 октября 2026 вернул **403: Upgrade to GitHub Pro or make this repository
public** для защиты веток и rulesets. Серверная защита на текущем тарифе недоступна.
Приватность сохранена. Локальные hooks можно намеренно обойти: абсолютной серверной
защиты от переписывания сейчас нет. После перехода на подходящий тариф включите
запрет force push/удаления main и version-control и запрет изменения/удаления тегов.

Сохранение на GitHub и workflow не развёртывают приложение и не меняют production.

## Состояние проверок исходного снимка

При настройке сохранения 11 октября 2026: 10 тестов механизмов безопасности и
восстановления прошли; C-launcher прошёл проверку компилятора с `-Wall -Wextra -Werror`.
Полный набор существующих тестов приложения: 64 теста, 22 провала и 34 ошибки.
Исходники и тесты текущей рабочей папки расходятся по поколениям; эти ошибки
сохранены как существующее состояние, без изменения функциональности приложения.
Для исправления нужен отдельный разбор. Успешный workflow сохранения подтверждает
безопасность снимка и механизма восстановления, а не исправность всего приложения.
